# 09. 마키마 코치 연동

내 제1비서관 **마키마**(OpenClaw)가 운동 채널에서 코치 역할을 하고,
반복 작업은 **헬스봇**(이 레포)에게 시키는 구조.

> 설정 파일과 cron 등록 스크립트는 별도 레포에 있다 → `para333311/secretary1`
> 이 문서는 헬스봇 쪽 인터페이스만 다룬다.

---

## 역할 분담

```
Windows 11 노트북 (24시간 ON)
│
├─ OpenClaw Gateway ── 마키마 [토큰 A · Grok → Gemini]
│    ├─ 나와의 DM   → 비서.  지금까지 하던 그대로
│    └─ cron 잡 3개  → 코치.  하루 3번만 깨어난다
│           ① python -m bot --brief --json   ← 내 데이터를 읽는다
│           ② Grok 이 코치 발언을 쓴다
│           ③ python -m bot --say "..." --by 마키마   ← 헬스봇에게 발행 지시
│
│    (컨디션 기록은 cron 이 아니라 헬스봇 /condition DM 명령으로 들어온다 — 아래 참조)
│
└─ 헬스봇 프로세스 ── python -m bot [토큰 B]
     ├─ 매시 정각 자극 (사진 / 명언카드 / 유튜브)   ← LLM 안 씀. 공짜
     ├─ 07:30 미션 · 12:30 응급처치 · 22:00 체크인 · 일 21:00 결산
     └─ DM 명령 수신 (/done /streak /weight, 사진 제출)
```

**채널에 글을 올리는 건 언제나 헬스봇이다.** 마키마는 채널 관리자가 될 필요가 없고,
자기가 쓴 글은 `— 마키마` 서명으로 구분된다. 마키마는 관리자, 헬스봇은 직원.

### 왜 이렇게 나눴나

| | 담당 | 이유 |
|---|---|---|
| 매시 자극 (하루 16회) | 헬스봇 | LLM 을 부르면 하루 16번 × 84일. 무료 티어가 버티지 못한다 |
| 정형 발행 (미션·체크인) | 헬스봇 | 템플릿으로 충분하고, 이미 검증돼 있다 |
| 코치 발언 (하루 3회) | 마키마 | 데이터를 읽고 매번 다르게 말해야 한다. LLM 이 필요한 부분은 여기뿐 |

LLM 호출은 **하루 3회**로 묶었다. 그록 프로 구독 안에서 돌아가고, 그록이 막히면
마키마의 기존 폴백(제미나이)이 그대로 작동한다. 추가 결제 없음.

## 헬스봇이 마키마에게 제공하는 4개 명령

### ① `--brief` — 내 데이터를 읽는다

```bash
python -m bot --brief          # 사람이 읽는 형태 (내가 확인할 때)
python -m bot --brief --json   # 마키마가 읽는 형태
```

```
2026-07-30 (목) · 유산소
3kg 프로젝트  D+7/84  1주차

연속        1일 (최고 1일)
이번 주     1/7      최근7일 ······■
누적        1일
쉰 날       어제부터 6일 연속
컨디션      2/5 (2026-07-30)  7일 평균 2.0
체중        78.4kg (2026-07-30, 0일 전)

flags: slipping, done_today
```

**핵심은 `flags` 다.** LLM 은 날짜 계산과 숫자 세기를 자주 틀린다. "며칠 연속
쉬었나"를 프롬프트 안에서 세게 두면 틀린 숫자로 독려하고, 그러면 신뢰가 깨진다.
그래서 판단은 파이썬이 다 하고 마키마는 해석만 한다.

| flag | 뜻 | 코치가 할 일 |
|---|---|---|
| `slipping` | 3일 이상 안 함 | 독려 강도 올림. 🟢부터 다시 권함 |
| `streak_at_risk` | 어제 안 함 | 가장 중요한 개입 시점. 오늘 끊기 직전 |
| `on_fire` | 5일 이상 연속 | 칭찬 + 과훈련 경고 |
| `needs_rest` | 컨디션 2 이하 3일 연속 | 🔴 말리고 휴식 권함 |
| `condition_stale` | 오늘 컨디션 기록 없음 | 코치는 묻지 않는다 — 운영자가 `/condition`으로 스스로 기록해야 꺼진다 |
| `weight_stale` | 8일 이상 안 쟀음 | 일요일에 상기 |
| `weight_stalled` | 최근 2회 차이 0.3kg 미만 | 운동 말고 270kcal(식사) 쪽으로 화제 전환 |
| `done_today` | 오늘 오운완 기록됨 | 밤에 같은 말 반복하지 않기 |
| `no_media_source` | 자극 소스가 하나도 없음 | 유튜브 채널 등록을 권함 |
| `season_over` | 84일 지남 | 시즌 결산 + 1주 휴방 안내 |

`published_today` 에 오늘 이미 발행된 잡 이름이 들어 있어서, 코치가 헬스봇과
같은 말을 두 번 하는 걸 막을 수 있다.

### ② `--say` — 헬스봇에게 발행을 지시한다

```bash
python -m bot --say "오늘 목요일이야. 계단 5층." --by 마키마
python -m bot --say "핀 메시지" --pin
```

`--by` 를 주면 본문 끝에 `— 마키마` 가 붙는다. 채널에서 누가 쓴 글인지 구분된다.
`--by` 없이 쓰면 평범한 헬스봇 발행이 된다.

### ③ `--record` — 데이터를 기록한다

```bash
python -m bot --record weight=78.4
python -m bot --record done=green          # green | yellow | red
python -m bot --record condition=4 --record done=yellow   # 한 번에 여러 개
```

형식만 검증한다 — 범위를 벗어나면(`condition=9`) 거부하고 종료 코드 1을 반환한다.

**컨디션은 코치가 먼저 안 묻는다.** 이 채널은 구독자가 답장할 수 없는 방송
전용 비공개 채널이라 채널에 질문을 올려도 답을 받을 방법이 없고,
`--session isolated` cron 세션은 답이 올 때까지 기다려주지도 않는다.
그래서 `condition=N`은 코치 cron이 아니라 **헬스봇 `/condition 1~5` DM 명령**으로
운영자가 직접 넣는다 (내부적으로는 같은 `--record`를 부른다).
자세한 경위는 [10번 문서](10-makima-handoff.md)의 단계 B3 참조.

`--brief` 와 `--record` 는 **채널로 아무것도 보내지 않으므로**
`TELEGRAM_CHANNEL_ID` 없이도, 인터넷이 끊겨 있어도 동작한다.

### ④ `--serve` — 수신 전용 모드

```bash
python -m bot --serve
```

내장 스케줄러를 끄고 DM 명령만 받는다. 발행 스케줄까지 OpenClaw cron 으로
옮기고 싶을 때 쓴다. **기본 구조에서는 쓰지 않는다** — 헬스봇의 내장 스케줄러가
매시 자극과 정형 발행을 그대로 담당하는 게 더 단순하고 LLM 비용이 0이다.

## 중복 발행을 막는 3가지 규칙

같은 미션이 두 번 올라가는 건 이 구조에서 유일하게 실재하는 사고다.

1. **GitHub Actions 워크플로를 끈다** — 단, **노트북 봇이 발행하는 것을
   확인한 다음에.** 노트북과 Actions 가 동시에 돌면 정확히 같은 글이 두 번
   올라간다.

   > ### 🛑 순서를 어기면 채널이 죽는다
   >
   > Actions 는 노트북에 봇을 깔기 전까지 **유일한 발행 주체**다.
   > 노트북 봇을 확인하기 전에 끄면 발행이 0이 된다.
   > 실제로 이 사고가 났다 — 노트북에 봇이 없는 상태에서 Actions 를 먼저 꺼서
   > 채널이 멈췄다.
   >
   > **끄기 전 체크리스트:**
   > - [ ] 노트북에 `helth_training` 이 있고 `.env` 에 토큰이 들어 있다
   > - [ ] 작업 스케줄러에 등록돼 `python.exe` 가 떠 있다
   > - [ ] `python -m bot --once photo` 로 올린 글을 채널에서 직접 봤다
   >
   > 셋째가 안 되면 **Actions 는 켜둔 채로** 고친다.

   워크플로 파일은 손대지 않고 GitHub 웹에서 끄는 게 안전하다
   (되돌리기도 클릭 한 번):

   https://github.com/para333311/helth_training/actions/workflows/publish.yml

   → **`Filter workflow runs` 검색창 바로 오른쪽의 `⋯`** → **Disable workflow**

   > 버튼이 두 종류라 헷갈린다. 각 실행 줄(`채널 발행 #8` …) 오른쪽에 달린 `⋯` 은
   > 개별 실행 메뉴(Re-run / Delete)라서 Disable 이 없다.
   > 필요한 건 목록 **위쪽**, 검색창과 같은 줄에 있는 `⋯` 이다.

   **꺼진 것을 확인하는 방법** (셋 중 아무거나):
   - 왼쪽 사이드바 워크플로 이름 옆에 `Disabled` 배지가 붙는다
   - 노란 배너 `This workflow was disabled manually` 가 뜬다
   - `Run workflow` 버튼이 `Enable workflow` 로 바뀐다

   예약 실행이 멈추고 수동 실행(Run workflow)도 함께 잠긴다.
   노트북이 며칠 꺼져 있었다면 `Enable workflow` 로 잠깐 켜서 수동 실행으로
   메꾸고, 다시 끄면 된다.

   > 워크플로 파일의 `schedule:` 을 주석 처리하는 방법도 있지만 권하지 않는다.
   > 나중에 브랜치를 병합하다가 조용히 되살아날 수 있다. 웹에서 끈 상태는
   > 저장소 설정에 남으므로 코드가 어떻게 바뀌든 유지된다.
2. **헬스봇 프로세스는 노트북에 하나만** 띄운다. 두 개 띄우면 같은 토큰으로
   둘이 폴링해서 텔레그램이 `409 Conflict` 를 던진다.
3. **마키마의 cron 잡은 헬스봇과 시간이 겹치지 않게** 짰다.
   헬스봇 07:30/12:30/22:00 → 마키마 07:40/19:00/22:20/일 21:20.

## 마키마가 채널에 자기 이름으로 뜨게 하고 싶다면

지금 구조에서 채널에 보이는 건 헬스봇 계정이고, 마키마는 서명으로만 존재한다.
마키마 아바타를 채널에 띄우려면:

1. 채널 → 관리자 → 마키마 봇 추가 → 권한은 **"메시지 관리"만** 켠다
2. `secretary1` 의 cron 잡에서 `--say` 대신
   `--announce --channel telegram --to "-1004448866091"` 을 쓴다

**바꾸기 전에 알 것:** 이러면 마키마 봇 토큰이 채널 쓰기 권한을 갖는다.
그만큼 토큰 유출 시 피해 범위가 커진다. 서명 방식이 더 안전하고, 실사용에서
"마키마가 말한다"는 감각은 서명만으로도 충분히 난다.

## 점검

```bash
python -m bot --brief                  # 데이터가 제대로 보이나
python -m bot --record condition=3     # 쓰기가 되나
python -m bot --brief | grep flags     # flag 가 반응하나
python -m bot --say "테스트" --by 마키마  # 채널에 서명이 붙어 나가나
```

`OWNER_USER_ID` 가 비어 있으면 `--brief` 가 빈 데이터를 돌려준다.
그러면 마키마가 "아직 시작도 안 하셨네요"만 반복하게 되므로,
연동 전에 `.env` 에 반드시 넣어야 한다.
